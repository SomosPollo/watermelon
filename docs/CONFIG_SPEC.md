# Configuration reference

`.watermelon.toml` is trusted host policy. Generate it with `init` or `clone`,
review it, and run `watermelon config validate`. Unknown keys are errors,
including fields inside mount entries.

| Change | Section |
|--------|---------|
| Automatic languages and managed source | [workspace and setup](#workspace-and-setup) |
| Base OS, name, or project access | [vm](#vm) |
| Allowed destinations | [network](#network) |
| Custom tools and global packages | [tools](#tools), [provision](#provision) |
| Additional host files | [mounts](#mounts) |
| Dev server access | [ports](#ports) |
| CPU, memory, and disk | [resources](#resources) |
| Blocking, discovery, or prompts | [security](#security) |
| Remote editor | [ide](#ide) |

Apply VM-affecting changes with `watermelon rebuild`; stop/start is insufficient.
Preserve needed VM-local system files first. Host source and managed workspace
disks remain. IDE-only changes need no rebuild. Manual `ask` configurations use
the CLI's foreground recreation instructions.

## `[workspace]` and `[setup]`

These sections are generated by `clone`/`init` and updated through `up`.
Use `up --runtime language=version,...` to review runtime changes instead of
hand-editing generated metadata. See [runtime support](WORKSPACES.md#runtime-and-dependency-support).

| Section / field | Meaning |
|-----------------|---------|
| `workspace.source` | Credential-free public GitHub HTTPS source |
| `workspace.disk` | Independently owned guest disk, bound to the canonical host settings directory |
| `setup.profile` | `node`, `python`, `go`, `rust`, `java`, `dotnet`, `ruby`, `php`, `cpp`, or `multi` |
| `setup.runtime` | Numeric runtime for one root project |
| `setup.manager` | Optional exact pnpm/Yarn or uv/Poetry pin for that root |
| `setup.only` | One-language restriction generated by `--template` for multi setup |
| `setup.runtimes` | One approved version per language in multi setup |
| `setup.projects` | 1–64 confined relative directories with `directory`, `profile`, and optional `manager` |

A generated mixed project looks like:

```toml
[setup]
profile = "multi"

[setup.runtimes]
node = "24"
python = "3.13"

[[setup.projects]]
directory = "frontend"
profile = "node"
manager = "pnpm@10.20.0"

[[setup.projects]]
directory = "backend"
profile = "python"
```

Each runtime needs a project. Generated `[tools]` declarations must provide
all profile commands from the matching runtime image. Combined/extended
profiles use a guest-built `watermelon-project:<hash>` image. Manager choices
and setup/workspace declarations participate in policy approval.

Managed workspaces require `vm.mount_project = false`,
`vm.workdir = "/workspace/project"`, no extra host mounts, no fixed VM-name
override, and no root provision scripts. Copying settings does not transfer
disk ownership. Automatic setup cannot combine with `[network.process]` or
global `[provision]` package lists. Omitted/empty `[setup]` means manual tools.

## `[vm]`

| Field | Default | Meaning |
|-------|---------|---------|
| `name` | Path-derived | Optional project-owned Lima name |
| `image` | `"ubuntu-22.04"` | `ubuntu-22.04` or `ubuntu-24.04` |
| `mount_project` | `true` | Mount the entire host project read-write at `/project` |
| `workdir` | `/project` when mounted; guest login directory otherwise | Working directory for shells, exec, and tools |

```toml
[vm]
image = "ubuntu-24.04"
mount_project = false
workdir = "/home/watermelon"
```

Fixed names must match `[a-z0-9]+(?:[._-][a-z0-9]+)*`, be at most 76 bytes,
and not end in `.yaml`/`.yml`. Names cannot adopt another project's or an
unmanaged Lima VM. `--name` overrides the setting for one command; see
[selection and recovery](COMMANDS.md#project-and-vm-selection).

An explicit workdir must be a clean absolute Linux path and already exist.
Watermelon validates it without creating it. For a custom manual VM, create
it during provisioning with `watermelon:watermelon` ownership. `run --workdir`
overrides one shell. With no mount/workdir, manual wrappers bind their current
guest directory. Narrow internal bootstrap/log mounts may still exist; see
[filesystem boundaries](SECURITY.md#filesystem-isolation).

## `[network]`

`allow` is a string array, empty by default. Behavior outside the list is
controlled by [enforcement](#security).

```toml
[network]
allow = [
  "registry.npmjs.org",       # Domain
  "*.githubusercontent.com",  # Subdomains only
  "example.com:443",          # TCP port restriction
  "192.168.1.1",              # IPv4; optional :port also supported
]
```

Wildcards do not include the apex and cannot have ports. The catch-all `"*"`
is invalid. A bare host/IP rule has no port or protocol scope beyond managed
DNS redirection. Allowed destinations remain possible data-exfiltration paths.

Workload TCP/UDP port 53 is redirected to a managed resolver. In `fail`/`silent`,
it answers only policy names; `log`/`ask` resolve arbitrary names. Exact names
are captured at trusted bootstrap; rebuild to refresh changed addresses.
Wildcard subdomains resolve dynamically. The managed resolver forwards permitted
lookups through `8.8.8.8`/`8.8.4.4`; trusted bootstrap uses Lima's DNS defaults.

Loopback, established/related responses, and scoped VM-control DHCPv4 traffic
remain available, even with `allow = []`. This is not arbitrary external UDP
access. Enforcement is IPv4-only: IPv6 is disabled in `fail`, `silent`, and
`ask`; `log` leaves it enabled and does not capture its events.

### `[network.process]`

Adds destinations for configured command wrappers in manual configurations:

```toml
[network]
allow = ["registry.npmjs.org"]

[network.process]
claude = ["api.anthropic.com", "*.anthropic.com"]
codex = ["api.openai.com"]
```

Rules are additive: general allowlist plus process rules. Unlisted commands
use only the general list. Invoke the configured wrapper to enter its dedicated
network namespace and resolver; `log` observes rather than enforcing the list.
The root-owned launcher has narrowly scoped authorization; general `sudo`
remains unavailable. Helper/namespace names are internal.

Keys must match `[A-Za-z0-9_][A-Za-z0-9._+-]*` and be at most 255 bytes.
At most 255 rules are supported, using `/24` subnets under `10.200.0.0/16`.
Automatic setup profiles do not support this section. See the
[assistant-in-VM example](examples/ai-coding-assistants/README.md).

## `[tools]`

Manual tools map a container image to exposed command wrappers:

```toml
[tools]
"node:20-slim" = ["node", "npm", "npx"]
"python:3.12-slim" = ["python", "python3", "pip"]
```

Commands become `/usr/local/bin` wrappers. Each runs a container with the VM's
network and a bind of `vm.workdir` (`/project` by default). In mounted manual
projects, shell `cd`, environment changes, and Python activation are not
inherited by tool containers. Use tool-specific options such as
`npm --prefix frontend test`, or automatic setup for shared runtime behavior.
No-mount wrappers use the configured workdir or their current guest directory.

Each command can appear only once. `nerdctl` and Watermelon's internal
`watermelon-npm`, `watermelon-pip`, `watermelon-cargo`, `watermelon-go`, and
`watermelon-gem` Docker Hub image names are reserved.

Images are pulled during trusted bootstrap before workload enforcement; no
workload registry grant is needed solely for those pulls. An empty command
list preloads an image without wrappers. Wrappers append arguments to the
image entrypoint; shell entrypoints may discard them. Use the
[Foundry helper](examples/foundry/README.md) when an explicit entrypoint is needed.

## `[provision]`

Global package lists apply to manual tools. Their package-manager command must
be declared in `[tools]`. Installation runs after network enforcement, so allow
required download destinations. Rebuild after changes to create CLI wrappers
reliably; ad-hoc global installation may not expose a new executable.

| Field | Install action |
|-------|----------------|
| `npm` | `npm install -g` |
| `pip` | `pip install` |
| `cargo` | `cargo install` |
| `go` | `go install` |
| `gem` | `gem install` |
| `scripts` | Embed host files and execute them as root in the guest |

```toml
[tools]
"node:20-slim" = ["node", "npm", "npx"]

[provision]
npm = ["typescript"]
scripts = ["./vm/setup.sh"]
```

Package specifications are individual quoted arguments. Leading `-`,
whitespace, controls, invalid UTF-8/NUL, quotes, and executable shell syntax
are rejected; version/URL operators remain literal manager input. Each active
manager needs its exact command in one image; two managers cannot provision
the same image.

Scripts must be idempotent, project-relative, current-user-owned regular UTF-8
files, with no NULs, symlink path components, or lexical `..`. Limits are
1 MiB each and 4 MiB total. They have root authority after network enforcement,
including without a project mount. Managed workspaces prohibit them.

Keep host scripts present and readable. `status`, `run`, `exec`, and `code`
reread exact bytes. Changes make the policy stale; missing/invalid inputs
prevent comparison and execution and may stop a verified running VM.
See [provisioning recovery](TROUBLESHOOTING.md#command-issues).

## `[mounts]`

Additional host paths are read-only by default:

```toml
[mounts]
"~/shared-data" = { target = "/mnt/watermelon/data" }
"~/build-cache" = { target = "/mnt/watermelon/cache", mode = "rw" }
```

Each entry requires `target`; `mode` is `ro` or `rw`. Targets must be unique
normalized descendants of `/mnt/watermelon`, without `..`. The root and
`bootstrap`/`state` subtrees are reserved. These restrictions prevent shadowing
system or policy paths. The separate default project mount is always writable.

Read-only files can still be read and copied. Guest apps need explicit paths
to mounted configuration; tool containers do not automatically receive every
guest mount. Custom container invocations need an explicit bind for additional
paths. Managed workspaces allow no extra host mounts.

## `[ports]`

```toml
[ports]
forward = [3000, 8000]
```

`forward` defaults to `[]`. Ports must be unique integers from 1–65535.
Host `127.0.0.1:PORT` forwards to the same guest port. Bind the guest app to
`0.0.0.0` and use its configured port. Rebuild after changing the list; it does
not remap ports or expose host services to the guest.
See [development servers](WORKSPACES.md#run-a-development-server).

## `[resources]`

| Field | Default | Accepted value |
|-------|---------|----------------|
| `memory` | `"2GB"` | Positive integer + uppercase `MB`, `GB`, or `TB` |
| `cpus` | `1` | Integer ≥ 1 |
| `disk` | `"10GB"` | Same size format; VM system disk |

Sizes cannot have leading zeros. For larger builds, for example:

```toml
[resources]
memory = "4GB"
cpus = 2
disk = "20GB"
```

Automatic profiles may generate larger disks. Managed source storage is
separate. Writable host mounts consume host storage outside VM disk limits.

## `[security]`

```toml
[security]
enforcement = "fail"
```

| Mode | Outside the allowlist | DNS |
|------|-----------------------|-----|
| `fail` (default) | Block; record rate-limited events | Policy names only |
| `silent` | Block without events | Policy names only |
| `log` | Allow; record IPv4 events only | Arbitrary names |
| `ask` | Prompt for TCP; reject other traffic | Arbitrary names |

`log` is permissive discovery. Restore `fail` and rebuild after reviewing
required destinations. IPv6 remains allowed and unrecorded in `log`.

`ask` needs one foreground `run`, `exec`, or `code` prompt controller per VM.
`run --no-shell` is rejected. On Linux, verdicts use the foreground controlling
terminal, with guest input paused during prompts; redirected stdin remains
exclusive to the guest. Without a controlling terminal, requests block.
macOS uses native dialogs. Direct SSH does not serve prompts.

**Always Allow and Save** immediately permits the literal IPv4/TCP endpoint
across all processes, then saves the displayed bare hostname (or IP) as a
broader global rule without process, port, or protocol scope. Finish the session
and use the exact VM-pinned recreation command printed by Watermelon. Until
then, checked execution refuses the stale policy and may stop the VM.
Hostname/process labels are informational; verdicts are cached by IP and port.
See [prompt attribution limits](SECURITY.md#network-isolation).

## `[ide]`

| Field | Default | Meaning |
|-------|---------|---------|
| `command` | `"code"` | Host CLI supporting VS Code-compatible `--remote` and `--wait` |
| `workdir` | `vm.workdir`, then VM default | Existing absolute guest directory for the editor only |

```toml
[ide]
command = "cursor"
```

Compatible CLIs include `code`, `cursor`, `codium`, and `code-insiders`.
Install Remote-SSH support. Watermelon stays foreground until the remote
window closes, retaining its usage lease and any ask controller.
With no mount/workdir, it leaves the remote directory to the editor.
Commands and paths reject shell injection syntax. See [editor setup](COMMANDS.md#watermelon-code).

## File Location

Watermelon checks the canonical current directory and physical parents for
the nearest config. It checks each directory before stopping at a `.git`
entry, filesystem boundary, untrusted parent, or filesystem root. Trusted
parents are current-user-owned and not world-writable, or root-owned and not
group/world-writable. Mode checks do not account for filesystem ACLs; review
shared-workspace access separately.

The selected config must be a regular file ≤4 MiB with the same ownership/mode
rules. A symlink to a trusted loadable file is supported. Invalid, unreadable,
or unsafe selected files fail without falling back to an ancestor. Reads use
the same opened descriptor.

The config directory becomes the project root for VM identity, mounts,
scripts, logs, and policy state. Host subdirectories do not become guest
workdirs; use `exec --cwd`. `status` prints the resolved `Project:` path.
`init` instead writes only in the exact current directory.

Normal `--name` commands require valid config and verified project ownership.
Management commands retain their historical current-directory target only
when neither config nor explicit name is present. See [recovery exceptions](COMMANDS.md#project-and-vm-selection).
